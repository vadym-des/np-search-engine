## 🏛️ Конституція Пошукового Рушія (Search Engine Invariants)
Будь-який агент або розробник у будь-якому новому чаті зобов'язаний дотримуватися залізних законів архітектури (детально описано в [`SEARCH_ENGINE_SPEC.md`](SEARCH_ENGINE_SPEC.md)):

1. **Робоча поштова мережа над «пустими» тезками (`branchCount > 0`)**:
   - При колізіях однойменних міст/сіл (`Малин`, `Павлів`) без вказаної області пріоритет має пункт із діючими відділеннями Нової пошти/Укрпошти. Пусті 0-відділкові села не обираються, якщо поруч є місто з діючою поштою.
2. **Ієрархія префіксів обласних центрів (`REGIONAL_CENTERS`)**:
   - У запитах виду `[Обласний центр] [Село] [Номер]` (наприклад: `львів павлів 1`, `житомир попільня 2`) обласний центр є **регіональним контекстом (областю)**, а цільовим містом доставки є село/селище. `parseQuery.matchedSettlement` обов'язково оновлюється на це село.
3. **Крос-перевірка вулиць проти сіл-тезок (`isStreetOfCity`)**:
   - Якщо назва збігається з вулицею діючого відділення міста (`вул. Культури` у Слобожанському), токен вважається **вулицею**, а не окремим селом (`село Культура`). Виклики вибірки та валідації вулиць обов'язково канонізуються через `canonCity(cityName)`.
4. **Розпізнавання подвійних номерів (Номер будинку + Номер відділення)**:
   - У запитах типу `культури 6 слобожанське 1` число після вулиці є номером будинку (`building: 6`), а останнє число — номером відділення (`targetBranchNumber: 1`). Якщо точного номера немає, система виводить відділення та поштомати з цієї вулиці, а не порожній екран.
5. **Суворий поріг Левенштейна**:
   - Для слів довжиною $< 6$ літер максимальна дистанція Левенштейна дорівнює **1** (захист від хибних збігів типу «варва» $\rightarrow$ «арка»).
6. **Відсутність хибного Did-You-Mean**:
   - Якщо назва міста/села буквально присутня в запиті (`isLiteralInQuery`), блок пропозицій «Можливо, ви мали на увазі» не відображається.

## 🔒 Протокол Запобігання Регресіям (Anti-Regression Mandate)
1. Кожен знайдений користувачем баг/артефакт **обов'язково додається як постійний тест** у `tests/test_google_like_cases.js`.
2. Перед будь-яким релізом чи пушем **обов'язково запускається повний тестовий сьют**:
   ```bash
   node tests/run_all.js
   ```
   Усі тестові модулі (150+ перевірок) повинні пройти з кодом `0` (100% green). Будь-який пуш при наявності помилок суворо заборонений.

## 🚀 Правило Пушу та Локальної Роботи (Local-Only & Strict Push Protocol)
**ЗАЛІЗНЕ ПРАВИЛО ДЛЯ ВСІХ ЧАТІВ (Local-Only by Default):**
- Будь-яка розробка, нові фічі, UI-покращення, багфікси та редагування файлів ЗАВЖДИ виконуються **виключно локально**.
- Агенту **суворо заборонено** самостійно виконувати `git push` на GitHub без явної команди користувача `push` або `пуш` (до цього моменту зміни залишаються лише локально для перевірки).

Коли користувач явно дає команду `push` або `пуш`:
1. **Перевірка версій**: Обов'язково актуалізувати версію у всіх точках проєкту:
   - `index.html` (кнопка версії у футері `.version-tag`, заголовок у модальному вікні та query-параметри підключення скриптів `?v=X.X.XX`);
   - `sw.js` (`CACHE_VERSION`, `CACHE_NAME` та `PRECACHE_ASSETS`);
   - `CHANGELOG.md`;
   - `tests/test_map_tiles_and_resilience.js`.
2. **Синхронізація гілок**: Оскільки GitHub Pages транслюється з гілки `gh-pages`, пуш ЗАВЖДИ виконується в обидві гілки:
   - Зафіксувати зміни на `main` та виконати `git push origin main`;
   - Переключитися або злити `main` у `gh-pages` (`git checkout gh-pages && git merge main`) та виконати `git push origin gh-pages`;
   - Повернутися на гілку `main` (`git checkout main`).
3. Користувач повинен завжди бачити найновішу версію сайту на GitHub Pages протягом 1 хвилини без застарілого кешу.

### Алгоритм виконання (6 кроків з інкрементальним запобіжником)
1. **Перевірка чекпоінту та інкрементальне зчитування логів**:

   - Зчитати живі логи через CLI `gsheets` (без запиту посилань у користувача):
     ```bash
     gsheets readonly read 1YwtdyqlHC3tHJL1WEPhlVw3gxkrl_rZd6C0QBlmNxTo "📊 Зведена аналітика!A1:C30"
     gsheets readonly read 1YwtdyqlHC3tHJL1WEPhlVw3gxkrl_rZd6C0QBlmNxTo "🔥 Сьогодні!A1:G200"
     gsheets readonly read 1YwtdyqlHC3tHJL1WEPhlVw3gxkrl_rZd6C0QBlmNxTo "📅 Останні 7 днів!A1:G300"
     ```
     *(Вкладки `🔥 Сьогодні` і `📅 Останні 7 днів` відсортовані від найновіших до старіших по колонці `A`: щойно досягнуто рядок із часом `<= lastAnalyzedTimestamp`, подальше гортання/дочитування діапазонів припиняється; до вибірки включаються **виключно** рядки з часом `> lastAnalyzedTimestamp`.)*
   - Якщо нових рядків (`> lastAnalyzedTimestamp`) немає, одразу повідомити про це користувача без повторного аналізу старих записів.
   - *(За потреби повного архіву також зчитувати `"Всі логи!A1:G500"` або `"🗓️ Останні 30 днів!A1:G300"`, так само фільтруючи по `> lastAnalyzedTimestamp`.)*
2. **Діагностика лише нових проблемних патернів**:
   - Серед рядків із часом `> lastAnalyzedTimestamp` відфільтрувати записи зі статусами `🔴 0 результатів`, `🔴 0 результатів (автокомпліт)`, `🔴 0 рез. ➔ Переписано`, `🟠 Переписування запиту`, `🟢 Успіх після переписування` (де в колонці `B` записано `«початковий запит» ➔ «фінальний запит»`), `🟡 Перемикання після невдачі`, `🟡 Немає НП (доступна Укрпошта)`, `🟡 Немає УП (доступна Нова пошта)`, `🟣 Кинутий пошук`.
   - Прогнати лише **нові** проблемні початкові запити через поточний `SmartSearchEngine` (`data/fuzzySearch.js`) у Node.js: усе, що вже успішно проходить на поточній версії рушія, пропускати, щоб фіксувати тільки реальні нерозв'язані збої.
3. **Покращення пошукового рушія**:
   - Внести точкові покращення в `data/fuzzySearch.js` або словники синонімів/скорочень із суворим дотриманням інваріантів `SEARCH_ENGINE_SPEC.md`.
4. **Захист від регресій**:
   - Додати всі виправлені запити з логів як постійні тести у `tests/test_google_like_cases.js`.
   - Запустити повний тестовий сьют `node tests/run_all.js` (усі 18 модулів мають пройти з кодом `0`).
5. **Оновлення чекпоінту (`telemetry_checkpoint.json`)**:
   - Після завершення аналізу зафіксувати у `telemetry_checkpoint.json` новий `lastAnalyzedTimestamp` (час найновішого перевіреного рядка з колонки `A`), актуальну версію, кількість оброблених нових рядків та дату/нотатку.
6. **Реліз та синхронізація гілок (лише після команди `push` / `пуш`)**:
   - Локально підготувати зміни (включно з оновленим `telemetry_checkpoint.json`) та відзвітувати користувачу про результати тестів; піднімати версію проєкту (`index.html`, `sw.js`, `CHANGELOG.md`, `tests/test_map_tiles_and_resilience.js`) та виконувати пуш в обидві гілки (`main` та `gh-pages`) **лише після явної команди `push` / `пуш`** (якщо користувач окремо не написав `і запуш` у початковому запиті).
