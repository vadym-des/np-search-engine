## 🏛️ Конституція Пошукового Рушія (Search Engine Invariants)
Будь-який агент або розробник у будь-якому новому чаті зобов'язаний дотримуватися залізних законів архітектури (детально описано в [`SEARCH_ENGINE_SPEC.md`](SEARCH_ENGINE_SPEC.md)):

1. **Робоча поштова мережа над «пустими» тезками (`branchCount > 0`)**:
   - При колізіях однойменних міст/сіл (`Малин`, `Павлів`) без вказаної області пріоритет має пункт із діючими відділеннями Нової пошти/Укрпошти. Пусті 0-відділкові села не обираються, якщо поруч є місто з діючою поштою.
2. **Ієрархія префіксів обласних центрів (`REGIONAL_CENTERS`)**:
   - У запитах виду `[Обласний центр] [Село] [Номер]` (наприклад: `львів павлів 1`, `житомир попільня 2`) обласний центр є **регіональним контекстом (областю)**, а цільовим містом доставки є село/селище. `parseQuery.matchedSettlement` обов'язково оновлюється на це село.
3. **Крос-перевірка вулиць проти сіл-тезок (`isStreetOfCity`)**:
   - Якщо назва збігається з вулицею діючого відділення міста (`вул. Культури` у Слобожанському), токен вважається **вулицею**, а не окремим селом (`село Культура`). Виклики вибірки та валідації вулиць обов'язково канонізуються через `canonCity(cityName)`.
4. **Розпізнавання подвійних номерів (Номер будинку + Номер відділення)**:
   - У запитах типу `культури 6 слобожанське 1` число після вулиці є номером будинку (`building: 6`), а останнє число — номером відділення (`targetBranchNumber: 1`). Якщо точного номера немає, система виводить відділення та поштомати з цієї вулиці, а не порожній екран.
5. **Суворий поріг Левенштейна**:
   - Для слів довжиною $< 6$ літер максимальна дистанція Левенштейна дорівнює **1** (захист від хибних збігів типу «варва» $\rightarrow$ «арка»).
6. **Відсутність хибного Did-You-Mean**:
   - Якщо назва міста/села буквально присутня в запиті (`isLiteralInQuery`), блок пропозицій «Можливо, ви мали на увазі» не відображається.

## 🔒 Протокол Запобігання Регресіям (Anti-Regression Mandate)
1. Кожен знайдений користувачем баг/артефакт **обов'язково додається як постійний тест** у `tests/test_google_like_cases.js`.
2. Перед будь-яким релізом чи пушем **обов'язково запускається повний тестовий сьют**:
   ```bash
   node tests/run_all.js
   ```
   Усі тестові модулі (150+ перевірок) повинні пройти з кодом `0` (100% green). Будь-який пуш при наявності помилок суворо заборонений.

## 🚀 Правило Пушу (Strict Push & Release Protocol)
Коли користувач дає команду `push` або `пуш`:
1. **Перевірка версій**: Обов'язково актуалізувати версію у всіх точках проєкту:
   - `index.html` (кнопка версії у футері `.version-tag`, заголовок у модальному вікні та query-параметри підключення скриптів `?v=X.X.XX`);
   - `sw.js` (`CACHE_VERSION`, `CACHE_NAME` та `PRECACHE_ASSETS`);
   - `CHANGELOG.md`;
   - `tests/test_map_tiles_and_resilience.js`.
2. **Синхронізація гілок**: Оскільки GitHub Pages транслюється з гілки `gh-pages`, пуш ЗАВЖДИ виконується в обидві гілки:
   - Зафіксувати зміни на `main` та виконати `git push origin main`;
   - Переключитися або злити `main` у `gh-pages` (`git checkout gh-pages && git merge main`) та виконати `git push origin gh-pages`;
   - Повернутися на гілку `main` (`git checkout main`).
3. Користувач повинен завжди бачити найновішу версію сайту на GitHub Pages протягом 1 хвилини без застарілого кешу.
